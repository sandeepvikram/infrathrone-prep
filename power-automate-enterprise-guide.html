The business says: "Clients are sending PDFs and we are manually checking them and forwarding for approval. We want to automate this."

5.2 Break the FLOW into STAGES

Don't think in terms of actions yet — think in blocks
1. Ingestion
2. Extraction
3. Validation
4. Approvals
5. Updates
6. Notifications
7. Logging

Stage 1: Ingestion & Validation

  • Document arrives
  • Basic checks (file type, size, location)

Stage 2: Extraction (OCR)

  • Send file to Azure OCR / AI Builder
  • Receive JSON with extracted fields

Stage 3: Business Validation & Routing Logic

  • Validate required fields (clientID, amount, signature)
  • Apply rules (amount thresholds, risk category)
  • Decide path: normal, high-risk, manual review

Stage 4: Approvals

  • Send to Relationship Manager
  • If needed, send to Compliance
  • Handle timeout / escalation

Stage 5: System Updates

  • Update SharePoint metadata
  • Update CRM / internal system
  • Possibly create a task in Planner/Jira

Stage 6: Notifications & Communication

  • Notify ops team / RM / onboarding team
  • Summary message in Teams / email

Stage 7: Logging & Audit Trail

  • Write to a "Log" list
  • Include document ID, decision, timestamps, approvers

Stage 8: Error / Exception Handling

  • If OCR fails → log + manual review route
  • If CRM update fails → log + retry or manual follow-up
I like to think of the flow in stages — input validation, extraction, business rules, approvals, system updates, notifications, and logging. That helps keep the flow readable and easier to maintain.

5.3 Decide the BRANCHES (Main vs Exception Paths)

Main Path (Happy Path)

  • OCR success
  • All required fields present
  • Amount < £250k
  • Risk = Normal
  • RM approves
  • CRM & SharePoint update succeed

Branch 1: High Value / High Risk

Condition: investmentAmount >= 250000 OR riskCategory = High

Action: Add Compliance approval step after RM

Branch 2: Missing / Invalid Data

Condition: Any critical field missing (clientID, amount, signatureFound = false)

Actions:

  • Route to Manual Review queue
  • Create a SharePoint item in ManualReview list
  • Notify Ops
  • Skip CRM update

Branch 3: Approval Timeout / Decline

Timeout Scenario:

  • If RM doesn't respond in 48 hours → Escalate to Line Manager + log

Rejection Scenario:

  • If RM rejects → Mark as Rejected
  • Notify Ops + client handler
  • No CRM update

Branch 4: System Failures

Potential Failures:

  • OCR API 500/timeout
  • CRM API fails
  • SharePoint update failure

For Those:

  • Log error
  • Send internal alert (Teams/Email)
  • Optionally retry or mark as "Pending Tech Support"

5.5 Define END STATES Clearly

For any good flow, you should be able to state all possible end states
End State 1: Completed – Approved
  • All approvals complete
  • CRM & SharePoint updated
  • Notifications sent
  • Log written with status "Approved"
End State 2: Completed – Rejected
  • RM (or Compliance) rejected
  • CRM left unchanged (or flagged)
  • Ops notified
  • Log written "Rejected"
End State 3: Completed – Manual Review
  • Missing / inconsistent data
  • ManualReview item created
  • Ops notified

When I design a flow, I'm very clear about the possible end states — Approved, Rejected, Manual Review, or Technical Failure. That makes it much easier for operations and support teams to know what happened with each document.

5.6 High-Level Design You Can SAY in the Interview

Question: "How would you design an automation for processing client documents with OCR and approvals?"

Your Answer:

"I'd trigger the flow when a new document is uploaded into a specific SharePoint library. From there, the first stage would be validation – basic checks on file type and size.

Next, I'd send the file to an OCR service like Azure Document Intelligence using HTTP or an AI Builder action, parse the JSON output, and validate that we have all the key fields like client ID, amount, product type and signature.

Then I'd apply the business rules – for example, if the amount is above a certain threshold or the risk category is high, I'd branch into an additional Compliance approval. Otherwise, it goes to the primary Relationship Manager.

Approvals would be handled through the Approvals connector, and once approved, I'd update SharePoint metadata and push the cleaned data into CRM, then notify the relevant teams on email or Teams.

Throughout the flow I'd log key events and, for any OCR or CRM failures or missing data, I'd route the item into a Manual Review queue with a clear log entry so nothing gets lost."

That sounds controlled, senior, and very relevant to SPW

6.3 Business Validation - Conditions & Switch

Step 1: Basic Completeness Check

Action: Condition Condition: varClientId is not empty AND varInvestmentAmount is greater than 0 AND varSignatureFound = true If NO → - Set varDecision = "ManualReview" - Create item in ManualReview list - Send Teams/Email to Ops - Go to log and end If YES → proceed

Step 2: Risk/Amount-Based Routing

Action: Condition (or Switch) If varInvestmentAmount >= 250000 OR varRiskCategory = 'High' → Requires extra Compliance approval If high value / high risk: - Set flag variable varIsHighRisk = true Else: - varIsHighRisk = false
I typically express business rules using Conditions and, where there are many categories, Switch blocks. For example, I'd branch high-value or high-risk investments separately to include a second Compliance approval step.

7.3 Configure Run After - The "Catch" for Failures

Example: After Scope – System Updates

Create two parallel branches:

  • Branch 1: OnSuccess - Normal flow continuation
  • Branch 2: OnFailure - Error handling

In Branch 2, Add Actions Like:

Compose / Set variable → varDecision = "Failed" Create item in FlowLogs with error info Notify support via Teams/Email

How to Set This Up

  • Click the three dots (...) on Scope – System Updates output action
  • Add a new step underneath
  • Click … → Configure run after
  • Select: has failed, has timed out, has been skipped

Now this path only runs on failure

I use 'Configure run after' a lot. For example, if my CRM update scope fails, a separate branch runs only on failure – it logs the error with the status code and notifies support so the item doesn't silently die.

Scenario 1: "A Flow is Failing in Production. Walk me through your troubleshooting."

Your Answer:

"First I go to the Flow → Run history to see the exact run that failed. I expand the error step and check its Inputs and Outputs. That usually tells me whether the issue is:

  • permission related,
  • a missing field from OCR,
  • a CRM API failure,
  • or a data shape change.

Next I go to Data → Connections to check if the service account lost permissions or if the token expired.

If it's OCR- or API-related, I compare a failed run with a successful one to see what changed. Then I update the log list with the RCA and notify support with next steps.

If it's a genuine bug, I fix it in Dev, test it in Test/UAT, and re-deploy a patched solution into Prod."

Scenario 2: "OCR suddenly starts returning inconsistent fields."

Your Answer:

"I'd first check the HTTP call output in run history to see what the OCR API actually returned. OCR models sometimes change their schema — a field might be renamed or nested differently.

If the schema changed, I update my Parse JSON schema, adjust variable mappings, re-test with real samples in Test, validate with business users, and redeploy through ALM.

Until then, any unreadable documents go through the Manual Review path with proper logging."

Scenario 3: "A manager didn't receive an approval email."

Your Answer:

"I would first check the Approvals section in the run history. If the approval was triggered, I check who it was assigned to. Sometimes the email was typed wrong, or the manager changed.

I verify the assigned email, check Outlook spam/junk, and confirm whether the Approvals connector is healthy. If needed, I re-trigger the approval or redirect it to the right person.

I also update the configuration (environment variable or SharePoint config list) so the next runs go to the correct approver."

Scenario 4: "CRM update failed with 403 forbidden."

Your Answer:

"That usually means the service account lost API permission. I check run history → Outputs → statusCode = 403.

Then I confirm:

  • which connection reference the flow uses,
  • which identity is bound in that environment,
  • and whether the service account still has the correct API scopes or Dataverse roles.

Once permissions are restored, I resubmit or re-run the failed item."

Scenario 5: "The manual review list is filling up. How do you handle that?"

Your Answer:

"I look at the logs to see why items are entering manual review. If it's because OCR is weak for certain templates, I collect samples and retrain the extraction model or adjust parsing logic.

If certain business rules are too strict, I review them with stakeholders.

Manual review should be a controlled path, not a sign of systemic failure."

Scenario 6: "How do you design a flow that depends on Azure Functions?"

Your Answer:

"I call the Function via HTTP and pass structured JSON input. The Function returns a JSON response which I capture with Parse JSON.

I always wrap Function calls in a Scope with run-after failure logic so I can route failures to Manual Review or alert support.

I also check with the Azure team what authentication method the Function uses — API key, OAuth, or managed identity via custom connector."

Scenario 7: "What if DLP blocks a connector you need?"

Your Answer:

"I check Flow Checker. If a connector is blocked, I speak with the admin to understand the policy.

Options are:

  • redesign the flow using allowed connectors,
  • move the flow to another environment where it's permitted, or
  • request an exception with justification.

The key is to stay compliant and never force unsupported architecture."

Scenario 8: "How do you handle performance issues?"

Your Answer:

"I check if the flow is doing heavy loops or processing large arrays. Sometimes I can optimise by:

  • changing SharePoint 'Get items' to filtered OData,
  • using parallel branches,
  • reducing unnecessary API calls,
  • or moving heavy processing to an Azure Function.

Then I check PPAC analytics for throttling or connector limits."

Scenario 9: "Your flow needs values from three systems. How do you avoid hardcoding?"

Your Answer:

"I store all URLs, emails, and endpoints as environment variables inside the solution. When moving Dev → Test → Prod, I fill the values per environment.

This keeps the flow portable and avoids broken references."

Scenario 10: "How do you version control your flows?"

Your Answer:

"In Power Platform, versioning is handled via solutions. Every time I export a managed solution for Prod, it creates a new version. I also keep documentation of changes in Confluence.

If needed, I can import a previous managed version to roll back."

Scenario 11: "A flow works in Dev but not in Prod."

Your Answer:

"That usually comes down to identity or configuration. I check:

  • connection references
  • service account permissions
  • environment variable values
  • DLP differences
  • API endpoint differences
  • missing permissions in SharePoint or CRM

Most issues are solved by aligning these."

Scenario 12: "An approval is stuck for 3 days."

Your Answer:

"I check the Approvals center to confirm the status. If the user simply didn't see it, I resend or escalate.

If the approval timed out due to business logic, I notify Ops, mark it as 'Stale' or 'Manual Review', and adjust logic so future approvals escalate earlier."

Scenario 13: "We need a chatbot that fetches answers from documents."

Your Answer:

"I'd build a Copilot Studio bot connected with Power Automate. The flow can:

  • take user query,
  • search SharePoint or a knowledge base,
  • fetch related content,
  • summarise or format the answer,
  • return result to Copilot.

If the logic gets heavy, I'd move the summarisation to an Azure Function."

Scenario 14: "How do you escalate errors to the team?"

Your Answer:

"I maintain a log list, but for high-severity issues I send a Teams alert to a specific channel. This includes the document ID, user, environment, and error description.

Ops can act immediately with all context."

Scenario 15: "What if a flow needs high availability?"

Your Answer:

"I design with retries, proper error paths, manual review fallback, and avoid heavy loops.

For mission-critical logic, I sometimes offload heavy compute to Azure Functions and keep PA as orchestration. This provides resilience."
