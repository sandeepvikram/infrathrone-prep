📋 Flow 1: LRDS Document Pre-Validation & Routing

A. Business Context

"For LRDS (Local Resident Discount Scheme), customers upload V5C and proof-of-address documents through the portal. These land inside Oracle Siebel CRM as service requests. The back-office team manually verifies whether the documents are valid (correct vehicle, correct address, not expired, readable etc).

This verification queue builds up heavily during month-end, and agents spend a lot of time checking basic things like: are both documents attached? Is the file readable? Does the SR have the right fields filled? Is the customer postcode within Dartford/Thurrock? Is the vehicle the same as the VRM on the SR?

The automation we built does the pre-validation and routing. It doesn't approve LRDS (that must be human), but it cleans the noise so back-office only works on correct cases."

B. Why We Built This Flow

  • Back-office team wasted time opening invalid cases
  • 20–25% of LRDS submissions had missing or wrong documents
  • Customers uploaded parking tickets, insurance PDFs, etc.
  • Backend CRM didn't warn users if incomplete
  • Back-office escalated to QA team that many issues could be pre-screened

Automation Goal: Reduce agent effort by filtering out invalid SRs, sending customers automated follow-up emails, and routing only valid submissions to back-office.

C. High-Level Flow Summary

Trigger: CRM "When a row is added, modified or deleted"

Actions:

  • Fetch attachments
  • AI Builder "Classify file" (light usage)
  • Postcode + VRM validation
  • Multiple condition blocks
  • Scopes for try/catch
  • Update CRM fields
  • Log to SharePoint list
  • Send Teams/Email alerts
  • Notify customer if docs missing
  • Route valid cases to LRDS queue

Technologies: Power Automate, CRM connector, SharePoint list, AI Builder (classification), Teams, Outlook

Identity: Runs using a Service Account with CRM read/write + SP contribute

D

Why This Trigger?

Trigger Used:

"When a row is added, modified or deleted" (Dataverse / Siebel CRM via custom connector)

Why:

  • LRDS SRs are created inside CRM automatically
  • Need near-real-time pre-validation
  • Trigger gives stable schema
  • No risk of per-item throttling like SharePoint
  • Internal HR/security requires CRM-first triggers

Considerations:

  • Runs only when SR type = LRDS and SR status = "Submitted"

  • Runs in default environment but deployed as solution-aware for governance

How Power Automate ↔ Azure Function Integration Works

🔄 Integration Flow

Step 1: Azure Function HTTP Trigger

Terraform provisions: Resource Group, Storage Account, Function App, App Insights

Function has: HTTP Trigger, Function Key OR Managed Identity enabled

Step 2: Identity Used

Pattern A - Function Key (freelance):

PA → HTTP Action → passes Function Key in header: x-functions-key: [key]

Pattern B - Managed Identity (enterprise):

Flow authenticates using Managed Identity or service principal through Azure AD

Step 3: Function → Graph API

Inside the function:

  • Validate payload received
  • Authenticate to Microsoft Graph using Managed Identity
  • Perform updates (group membership, metadata, etc.)
  • Write logs to App Insights
  • Return 200 + message on success, 4xx/5xx on error

Step 4: Function Responds

PA flow reads response: 200 OK → success, 400/500 → tech/business error

🎯 Your Interview Script (Short, Crisp, Perfect):

"We integrated Power Automate with Azure Functions through an HTTP-triggered endpoint. The Function App was provisioned with Terraform, and we exposed a secure HTTPS URL.

In Power Automate, we used the HTTP action and authenticated using the Function Key in the header. In an enterprise environment like SPW, we can also use Managed Identity for stronger governance.

Power Automate sent a clean JSON payload to the function — things like RequestId, decision, and M365 target.

The Azure Function handled all heavy logic, including Microsoft Graph API operations. It authenticated to Graph using its Managed Identity, where we granted only the minimum required permissions.

The function returned a 200/400 response that Power Automate used to update SharePoint and drive logging and error paths.

This design kept Power Automate simple, pushed complex logic into Azure, and followed a least-privilege identity model that's aligned with enterprise governance."
