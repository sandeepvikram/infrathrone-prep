📋 Flow 1: LRDS Document Pre-Validation & Routing

💬 Interview Explanation:

Context: At Conduent, we were seeing about 20-25% of LRDS service requests coming through with missing or unreadable documents, which meant our back-office teams were wasting time chasing customers for the right paperwork.

What I Built: I designed this pre-validation flow that acts as a quality gate at the front door. When a customer uploads documents for an LRDS request—like their V5C or proof of address—the flow triggers automatically and checks if the mandatory documents are actually there and readable. Based on the validation, it either routes the SR straight to the LRDS back-office queue if everything's good, or sends an automated email back to the customer asking them to provide the correct files.

Impact: This stopped those incomplete SRs from even hitting the back-office queues, which saved the ops teams from having to manually follow up with customers. We basically filtered out the bad requests upfront rather than discovering problems later in the process.

⚡ Quick Facts:

  • Scope: Internal, AFTER SR created in CRM
  • Trigger: When row added/modified in CRM (Dataverse connector)
  • Problem: 20-25% of LRDS submissions had missing/wrong documents
  • Goal: Filter out invalid SRs so back-office only works on correct cases
  • Innovation: Better routing + safer logic (null checks, switch cases, SP logging)

🔧 Tech/Tools:

  • Power Automate (cloud flow)
  • CRM/Dataverse connector (trigger + update)
  • SharePoint list (logging)
  • AI Builder (light usage - document classification)
  • Teams/Outlook (notifications)
  • Service Account (identity)

📝 Flow Steps (Abridged):

  1. Trigger: CRM row created/modified (LRDS SR type only)
  2. Fetch attachments: Get V5C and proof-of-address files
  3. AI classify: Check if doc types match expected (optional step)
  4. Validate: Check postcode in Dartford/Thurrock, VRM matches, both docs present
  5. Route: Valid → LRDS Queue | Invalid → Send email to customer asking for correct docs
  6. Log: Write decision to SharePoint RoutingLog (SR ID, route, reason, timestamp)
  7. Notify: Teams message to ops if issues detected

💬 Interview One-Liner:

"Flow 1 validates LRDS document submissions, checks if the right docs are attached and readable, routes valid cases to back-office, and auto-emails customers for missing docs. It reduced agent effort by filtering out 20-25% of invalid submissions."

💳 Flow 2: Payment/Penalty Pre-Validation & Routing

💬 Interview Explanation:

Context: Payment and penalty service requests have stricter requirements than regular LRDS cases because they involve financial transactions and tight SLAs. We couldn't afford to have ops teams working with incomplete financial data—things like missing vehicle registration numbers or invalid tariff amounts.

What I Built: This flow specifically handles payment and penalty SRs with enhanced validation rules. When one of these SRs is created in the CRM, the flow triggers and validates all critical financial fields—the vehicle registration mark, crossing date, tariff amount, and outstanding balance. If any field is missing or doesn't make sense, like a negative balance or blank VRM, it flags the SR as incomplete and routes it to a manual review queue. If all validations pass, it automatically routes to the appropriate payment operations queue.

Impact: This reduced manual rework by around 30% because we caught data quality issues immediately instead of ops teams discovering them mid-process. It also helped us maintain our SLAs because valid cases could flow straight through without delays.

⚡ Quick Facts:

  • Scope: Internal, ONLY payment/penalty related SRs
  • Trigger: CRM row created (SR type = Payment Failure / Penalty Dispute)
  • Problem: Payment SRs had repetitive issues (expired card, invalid CVV, missing transaction ID)
  • Goal: Pre-classify payment/penalty SRs so agents only work on genuine disputes
  • Difference vs Flow 1: Specialized financial/penalty rules, stricter validation, different queues

🔧 Tech/Tools:

  • Power Automate (cloud flow)
  • CRM/Dataverse connector (trigger + update + get rows)
  • SharePoint list (logging)
  • AI Builder (optional text classification on customer notes)
  • Teams (internal notifications)
  • Service Account (identity)

📝 Flow Steps (Abridged):

  1. Trigger: CRM row created (payment/penalty SR types only)
  2. Validate critical fields: Plate number, crossing date, tariff, balance present and not null
  3. Check payment status: Compare crossing date vs payment timestamp
  4. Classify: Extract reason codes (expired card, insufficient funds, invalid CVV)
  5. Route: Complete data → Payment Ops Queue | Missing data → Manual Review Queue
  6. Log: Write to SharePoint log (SR ID, classification, route, timestamp)
  7. Notify: Teams notification for escalations

💬 Interview One-Liner:

"Flow 2 validates payment and penalty SRs by checking financial fields like plate number, crossing date, and balance. It routes complete cases to payment ops and flags incomplete ones for manual review, reducing back-office rework."

🔧 Flow 3: Customer Self-Service Pre-Check (WIP)

⚠️ THIS IS YOUR INNOVATION STORY

This is WIP (Work in Progress) - you proposed it, validated with team, built early modules. NOT fully live in production.

💬 Interview Explanation:

Context: After working with the document validation and payment SR validation flows, I realized we were catching problems too late in the process. SRs were already created in the system, documents were already uploaded, and then we'd discover issues. I saw an opportunity to catch these problems even earlier—right at the submission point before anything hits our back-office queues.

What I Built: I proposed this comprehensive pre-check flow that acts as a unified validation gate before SRs enter the system. When a customer submits through the self-service portal, this flow triggers first and runs a complete validation suite: it checks if mandatory documents like V5C and proof-of-address are attached, validates that key fields like VRM, postcode, and customer email are populated, and even verifies LRDS eligibility by confirming the postcode is in the Dartford or Thurrock catchment area. Based on these checks, it intelligently routes the SR down one of three paths: if everything's complete and valid, it marks the SR as 'ReadyForProcessing' and passes it to the specialized flows. If documents or fields are missing, it immediately sends an automated email to the customer with specific instructions on what's needed. If the request isn't eligible at all, it routes to a dedicated 'Incomplete SR' queue for manual triage.

Impact: This became the refined approach that consolidated our validation logic into a single entry point. Instead of having separate flows catch different types of errors at different stages, we now stop incomplete requests at the front door. This significantly improved our first-time-right submission rate and meant the downstream validation flows only had to handle edge cases rather than basic data quality issues.

⚡ Quick Facts:

  • Scope: At the FRONT, BEFORE SR hits main queues (NOT after like Flow 1 & 2)
  • Trigger: When new SR created in certain categories OR customer submits form
  • Problem: 30-40% of SRs had incomplete data, forcing back-office to chase customers
  • Goal: Catch bad SRs upfront and either fix automatically or route to special bucket
  • YOUR Innovation: "Before, ops dealt with bad SRs AFTER they landed. Now, we catch upfront."

🔧 Tech/Tools (PoC Modules):

  • Power Automate (cloud flow)
  • CRM/Dataverse connector (trigger + update)
  • SharePoint list (logging + config)
  • AI Builder (document classification - optional)
  • Outlook (auto-email to customer)
  • Service Account (identity)

📝 Flow Steps (PoC - Abridged):

  1. Trigger: SR created in certain categories (LRDS, Payment, General)
  2. Check doc type: Is V5C attached? Is proof-of-address attached?
  3. Validate mandatory fields: VRM, postcode, customer email present?
  4. LRDS eligibility check: Postcode in Dartford/Thurrock?
  5. AI Builder (optional): Classify document type if filename unclear
  6. Route decision:
    • All checks pass → Mark SR as "ReadyForProcessing"
    • Missing info → Send auto-email to customer asking for docs
    • Not eligible → Route to "Incomplete SR" queue
  7. Log: Write decision to SharePoint pre-check log

💬 Interview One-Liner:

"Flow 3 is a front-door pre-validation layer I proposed. It checks SRs BEFORE they hit queues, validates doc types and mandatory fields, and either marks them ready or auto-emails customers for missing info. This reduces ops time wasted on incomplete cases by catching problems upfront."

☁️ Flow 4: Freelance Exception Approval Automation

💬 Interview Explanation:

Context: This was a freelance project where the client had a major process problem—people were emailing random managers for exception approvals with no clear process, no tracking, and no one knew who was supposed to approve what. It was creating bottlenecks and confusion.

What I Built: I designed a Power Automate flow that triggers when someone submits an exception request to a SharePoint list. Instead of using built-in Power Automate approvals, I integrated with an Azure Function that handles the complex routing logic. The Function calls Microsoft Graph API to look up manager hierarchies, department information, and applies business rules to determine the correct approver based on request value, department, and urgency. The Function returns the approver's details back to Power Automate, which then sends a structured approval request via email or Teams. Once the approver responds, the flow updates the SharePoint list with the decision and notifies the requester. The whole infrastructure was provisioned using Terraform for repeatability. I designed the Power Automate flow and the integration contract between PA and the Azure Function, while a senior engineer handled the Terraform provisioning and the core Function structure.

Impact: This replaced the chaotic email-based process with a structured, trackable approval workflow. It also demonstrated I could integrate Power Automate with Azure services and work with APIs beyond the standard connectors when business logic gets complex.

⚡ Quick Facts:

  • Business Problem: People emailed random managers, no one knew who approves what, no tracking
  • Trigger: SharePoint item created (ExceptionApprovals list)
  • Goal: Automated approval routing using identity data from Azure AD
  • Architecture: PA orchestrates, Azure Function handles routing logic, Graph API provides identity data
  • Your Role: PA flow design, integration contract, routing requirements (senior engineer did Terraform + Function structure)

🔧 Tech/Tools:

  • Power Automate: Orchestration, approvals, SP updates
  • SharePoint: ExceptionApprovals list, logging list
  • Azure Function: C# (.NET 6), HTTP trigger, routing logic
  • Microsoft Graph API: Get manager, department, groups from Azure AD
  • Managed Identity: Function authenticates to Graph (no passwords)
  • Terraform: Provisioned Resource Group, Storage, Function App, App Insights
  • Power BI: SLA tracking dashboard
  • PowerShell + Graph: Bulk sync jobs (separate from main flow)

📝 Flow Steps (Abridged):

  1. Trigger: SharePoint item created (Status = "New")
  2. Initialize variables: RequestID, Type, Amount, RiskLevel, SLADeadline
  3. Call Azure Function (HTTP): Send JSON with RequestID, RequestorEmail, Type, Amount
  4. Function logic:
    • Authenticate to Graph via Managed Identity
    • Get requestor's manager, department from Azure AD
    • Apply business rules (discount < £5k → Manager, £5k-£15k → Finance, > £15k → Director)
    • Return JSON: primaryApprover, backupApprover, requiredLevel
  5. PA reads response: If statusCode 200 → create approval, route to approver | If not 200 → log error, notify admin
  6. Approval outcome: Update SP with Approved/Rejected, record date/time/comments
  7. Log: Write to SP log list

💬 Key Interview Points:

  • Why C#? "Microsoft Graph SDK for .NET, strong typing, enterprise standard for production Azure Functions"
  • Why Azure Function instead of PA? "Routing logic too complex for PA (nested conditions), Function handles it cleanly with proper if/else, logging, and can be reused by multiple flows"
  • How PA + Function integrate? "PA sends JSON via HTTP, Function returns statusCode + JSON response, PA checks 200 = success or not 200 = error"
  • Why not Graph directly in PA? "Enterprise DLP often blocks Graph connector, Function (internal + trusted) always allowed and can call Graph with higher permissions"

💬 Interview One-Liner:

"Flow 4 automates exception approvals by using Azure Function to query Microsoft Graph for manager and department info, applying business routing rules, and returning the correct approver to Power Automate. PA sends the approval and tracks the result in SharePoint. I designed the PA flow and integration contract; a senior engineer handled the Terraform and Function structure."

💡 Why Azure Function Instead of Just Graph API?

🎯 Core Answer (Memorize This):

Graph = "Here is data from Azure AD"

Azure Function = "Here is the decision logic"

Graph only gives raw identity data (manager, department, groups). It does NOT decide who should approve, when to escalate, or what business rules apply.

7 Reasons (Quick Version):

Reason Explanation
1. Graph = Identity Only Gives manager/department, but NOT who approves, when to escalate, business rules
2. PA Can't Handle Complex Nested conditions become messy, hard to maintain, brittle
3. Full Control Proper if/else rules, query APIs, apply exceptions, add logging
4. Fast + Light PA slows with many conditions; Function handles instantly
5. Scalable Security Function can validate JWT, use Key Vault, retry logic, App Insights
6. Reduces DLP Blocks Graph connector often blocked by DLP; Function (internal) always allowed
7. Centralized Logic 1 Function for all flows; update once, applies everywhere

🎯 Final Interview Sentence:

"Graph gave us the raw identity data, but the routing logic itself — especially exceptions, escalation rules, group checks, discount thresholds, and fallback paths — was too complex to maintain inside Power Automate. So we pushed the business logic into an Azure Function, which let us write proper branching, add logging, use managed identity securely, and keep the flow clean. Power Automate only handled the orchestration; the Function did the decision-making."
